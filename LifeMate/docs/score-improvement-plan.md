## Implementation order

1. **Make the baseline reproducible.** Keep the submitted source, models and settings as the comparison point. Run paired reference-transcript and audio inference on the same frozen 309 organizer-train cases. Use a fixed, stratified subset for rapid iteration and the full 309 for candidate selection. There are 211 multi-call cases, 196 with history, 50 requiring clarification and 24 with empty gold traces, with overlap between those groups. Report final-state match, state-gated tool-call F1, first action accuracy, clarification precision and recall, unsafe or duplicate writes, repeated reads, and timing. Add a leave-app-out evaluation with multiple app families. Exclude their examples and tool demonstrations from fitting or retrieval while exposing each sample’s legitimate installed schemas at inference. The public catalog has 34 tool names absent from the train catalog. Measure score differences per scenario and report uncertainty. [Existing evaluator](../src/lifemate/metrics/reports.py#L93) · [Frozen split code](../src/lifemate/data/splits.py)

2. **Fix reference resolution and repeated reads first.** The spike found that the submitted reference checker rejected 152 correct labeled calls in 118 of 309 holdout cases. Bills, calendar updates and cancellations, bank transfers and chat messages account for 68 rejections and all reference failures in 52 cases. Match IDs to live results using request evidence such as bill type, due date and amount, calendar title and time, account balance and beneficiary, or chat participants. Require the evidence to identify the selected record and keep the checks for unknown IDs, wrong collections and genuinely ambiguous matches. Add a regression replay through the production pre-call checks. The public run also repeated an identical read without a new write 380 times across 80 cases, while the 309 reference traces contained none. Reuse successful identical read results within a sample until a relevant state change. Give empty reads a bounded, evidence-based reformulation path. Test intentional repeat writes and reads after state changes. [Reference resolution](../src/lifemate/runtime/references.py#L89) · [Execution loop](../src/lifemate/runtime/loop.py#L117)

3. **Train a schema-driven next-action policy.** Compare the repaired controller with a Qwen3.5-4B policy that selects the next `CALL`, `ASK` or `DONE` from the installed catalog, structured history and live results. Use one shared prompt for trajectory training and inference, including the same formatting and normalization. Start with one and two epochs on the authorized fit partition, using complete trajectories and realistic ASR transcripts alongside reference text. Inspect checkpoint quality before adding recovery examples or more epochs. Make pre-call validation and write deduplication part of the normal execution path. When the planner and action policy disagree, reassess the request and ground any write in explicit intent and live evidence. The public run had 145 cases where an empty plan suppressed a proposed call, including 107 proposed reads. A simpler planner alone scored 0.00 on the 16-case audio diagnostic. [Execution loop](../src/lifemate/runtime/loop.py#L148) · [Prompt builder](../src/lifemate/runtime/context.py#L31) · [Trajectory builder](../src/lifemate/learning/trajectories.py#L19)

4. **Test Gipformer against PhoWhisper-medium.** Add the base Gipformer 1.5 68M ONNX checkpoint as a CPU ASR candidate. Pin the eligible upstream revision and test on the same audio and action policy. Compare exact names, amounts, times, negation and corrections, then compare final-state and tool-call scores. The local PhoWhisper adaptation lowered WER from 31.65% to 30.39% on 64 utterances while the 16-case end-to-end score fell from 12.50 to 6.25. If the base Gipformer improves end-to-end results, evaluate fine-tuning on authorized fit audio, including eligible historical turns, with spoken-number targets and controlled speed/noise augmentation. [Gipformer model card](https://huggingface.co/g-group-ai-lab/gipformer1.5-68M-rnnt) · [Local ASR experiment](../../local_lifemate_artifacts/runs/public-full-20261114-102402/zalo-public-receipt.md)

5. **Close the gap on unseen apps and multi-step requests.** Rank remaining errors by lost score. Focus on missed prerequisites, conditional actions, relative dates, wrong argument values and clarification before lookup. Reuse deterministic normalization for arithmetic and dates, with provenance from the request, profile, history or live results. Test fit-only retrieval as an ablation using anonymized example structure, with current IDs and arguments filled independently. Datyth’s team measured an 11.1-point familiar-to-unseen gap with Qwen3.5 on its own test, and its first synthetic-app augmentation reduced its reported public score. Try additional training data only for a measured failure family, with executable validation and a held-out comparison. [Participant error analysis](https://github.com/Datyth/ZaloAI-Challenge-lifemate/blob/6ef76e00647bf44e14bcb084b58ef0c503584f55/docs/error_analysis.md)

6. **Verify the release end to end.** Use the same candidate for local evaluation and Docker. Pin weights, configuration, decoding and runtime. Rehearse offline on Linux CUDA with a read-only split mount, one official `ToolEnv` per sample, and all recorded calls and hashes returned by that session. Verify both validators on all 634 public rows, script/notebook output parity, repeatability, and the 30-second limit on the full request including history audio. Confirm the published limits of fewer than 6B total parameters, fewer than 5B LLM parameters, and 16,384 context tokens. Measure resource use on the RTX 3060 and validate the release on organizer-class hardware when available. [Release checklist](milestones/06-zalo-submission.md) · [Zalo LifeMate portal, Rule tab](https://challenge.zalo.ai/portal/lifemate)

## Score checkpoints and competition window

Use **30, 60, 80 and 90** as decision checkpoints on official scores when public evaluation is available. These are targets for successive candidates, with no assumed gain assigned to a particular code change. Use the frozen audio holdout and leave-app-out results to select candidates. A local score of 90 by itself cannot establish a public score of 90, especially if unseen apps underperform. The official result is the measure of success.

Use organizer train data for fitting, retrieval and development measurements. Use public and private inputs for final evaluation through their respective SDKs. At the submitted run's throughput, a 64-case audio pilot would take roughly 11 minutes and a 309-case pass roughly 52 minutes on the RTX 3060. These are planning estimates. Use the same saved case IDs for baseline and candidate pilots, and reserve full passes for candidates that improve final-state match and call score together.

- **14 November:** Reproduce the paired baseline, begin the reference and repeated-read fixes, and stage the release image requirements. Run a Gipformer base comparison if the model can be prepared in time.
- **15 November:** Compare the repaired runtime, the first policy checkpoint and the ASR alternatives using the same evaluation. Exercise the offline Docker entrypoint while models train or evaluate.
- **16 November:** Reserve time for a full run, validation, archive export, checksum and upload. The current Windows public run took roughly **1 hour 46 minutes**. Freeze the strongest verified eligible build in time for the **23:59 Vietnam time** solution deadline. If the score is below 90, record the gap and freeze that candidate if entering the private round. [Official timeline](https://challenge.zalo.ai/#timeline)

After freeze, run the submitted image on the private split and submit the result by **23 November at 23:59 Vietnam time**. Any later development toward 90 belongs to a separate iteration. [Official timeline](https://challenge.zalo.ai/#timeline)

The first implementation task is the reference and repeated-read fix with replay regressions. The first larger model investment is trajectory training against the corrected runtime. The published experiments support that order. They leave reaching 90 in this competition window unverified.
